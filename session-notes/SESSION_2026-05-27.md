# Session Notes — 2026-05-27

## Work Completed

### 1. LinuxCNC monitoring setup
- Built a HAL pin polling script (`/tmp/lcnc_monitor.sh`) that watches both joint
  f-error, faulted, amp-fault, and position pins at 10 Hz during program runs.
- Identified two errors from the LinuxCNC print log:
  - `Nested comment found` — repeated on every program run due to `()` comments
    containing inner `()` text in the generated G-code.
  - `Linear move on line 42 would exceed Z's negative limit` — Z soft limits were
    too tight for the test program.

### 2. Z soft limits changed
- Changed `[JOINT_1]` and `[AXIS_Z]` in `industry-cam.ini`:
  - Was: `MIN_LIMIT = -0.01`, `MAX_LIMIT = 23.5`
  - Now: `MIN_LIMIT = -3.0`, `MAX_LIMIT = 3.0`
- X limits left unchanged (`-0.01` to `4.25`).

### 3. G-code writer — comment format fixed
- `GCodeWriter._line()` was wrapping comments in `(text)` parentheses.
  Several comment strings themselves contained `(prev pass)` / `(clears shoulder)`
  creating nested comments that LinuxCNC's RS274 parser rejects.
- Fixed: switched to `;` trailing comments throughout. Semicolon comments are
  immune to nesting — parentheses in the comment text are treated as plain text.

### 4. G-code writer — RS274 delimiters and cutter comp
- Added `%` as the first and last lines of every generated program (RS274 standard
  file delimiters). LinuxCNC's cutter-comp look-ahead pre-scans the entire file;
  without `%` some builds report "file ended with no percent sign or program end (M2)".
- Added trailing newline after the closing `%`.
- Replaced `G41`/`G42` cutter radius compensation with `G40` (comp off). Cutter comp
  requires a tool radius entry in `tool.tbl`; with no radius configured (T99 has none),
  G42 triggers a look-ahead failure that surfaces as the "file ended" error.
  Re-enable once tool radii are entered in the tool table.
- Replaced em dash (`—`) in the program header with ASCII hyphen (`-`) to avoid any
  non-ASCII bytes being parsed by the C-based RS274 interpreter.

### 5. Status bar DRO — larger position readout
- Increased ribbon height to 54 px (was 48 px).
- Added a bordered DRO box containing X and Z with 34 pt monospace font.
- Secondary elements (RPM, feed, tool, G-codes, buttons) reduced by ~25% to
  compensate for the taller ribbon.
- Fixed a Qt stylesheet cascade bug: per-widget `setFont()` is overridden when
  `setStyleSheet()` is also called on the same label while a global
  `QWidget { font-size: 10pt; }` stylesheet is active. Fix: include `font-family`
  and `font-size` explicitly in each DRO label's own stylesheet string.

### 6. Run tab — live toolpath display
- `MachiningGraphWidget`: enlarged tool dot (size 10 → 16, dark outline), added
  `highlight_next_segment(move_index)` which draws the upcoming segment as a white
  dotted line.
- `SimViewerWidget`: added `_line_to_sim_idx` mapping (G-code line → SimMove index)
  built at load time. Added `update_live_position(motion_line, x_r, z)` which:
  - updates the tool dot from live machine position,
  - reveals all executed toolpath segments up to the current G-code line,
  - previews the next segment as a dotted line.
- `RunTab._poll()`: switched from calling `set_tool_position` directly to calling
  `update_live_position`, passing the LinuxCNC `motion_line`. Clears the next-segment
  preview when execution goes idle.

## Known Bugs — Not Fixed This Session

### Bug: G-code writer defaults tool to T1
The generated G-code uses `T1` (or some default) instead of the tool number the user
selected in the Program tab. The tool selection from the UI is not being propagated
correctly to `GCodeWriter.write()`. Needs investigation in the pipeline path from the
Program tab tool selector → `PlanResult.tool` → `GCodeWriter`.

### Bug: Tool selector widget — keyboard input not supported
The tool number selector in the Program tab (and/or Tools tab) only supports scrolling
to select a tool number; it does not accept direct keyboard entry of a tool number.
This is severely limiting when tool numbers are non-contiguous — e.g., T6 through T99
with nothing in between requires many scroll steps. The widget should accept typed
input directly.

### Bug: "File ended with no percent sign" error persists intermittently
Even after adding `%` at the start and end of the generated program, the error
"File ended with no percent sign (%) or program end (M2)" still appeared on the
first facing pass and paused execution. The program would not restart on Cycle Start.

**Observed workaround:** powered the spindle off and back on, then hit Cycle Start
again — execution proceeded normally.

**Unclear causation:** it is not known whether the spindle power cycle directly cleared
the condition, or whether the error had already cleared on its own in the time it took
to cycle the spindle (i.e., a time-dependent LinuxCNC interpreter state reset). The
error may be transient and related to the interpreter's internal state from a previous
failed run rather than a persistent file-format problem.

**Hypothesis to investigate:** LinuxCNC's task/milltask may cache interpreter state
between runs. If a previous run ended in an error (e.g., the earlier nested-comment
failures), the interpreter might be in a bad state that causes the next file open to
mis-parse. Hitting Reset → Machine On → Cycle Start in sequence (rather than just
Cycle Start after an error) may be required to fully reset the interpreter. The spindle
power cycle may have just forced a pause long enough for the operator to go through
that sequence.
